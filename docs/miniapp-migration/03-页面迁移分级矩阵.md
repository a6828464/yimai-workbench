## 0. 一句话结论

一麦的迁移不是「把 27,911 行 Vue 页面搬到小程序」，而是**「重写 15,145 行 SFC 呈现层（54.2%）+ 复用 16,331 行逻辑层与存储底座（81.8%）」**——因为业务页面**没有把 Element Plus 当 UI 基座裸用到底**：它已经有一层 `MobileCard` 卡片化降级（26 个文件引用、15 页已实测通过）、一套三档断点、以及把 9 个 api 文件全部收口到单个 `backend.ts` 传输层的结构。

**最关键的一条负面修正**（见 §5.7 撤回记录）：`api/` 表面上「只有 3 个文件碰 localStorage」，但沿 import 链走到叶子，`api/yimai.ts` 会拉起 75 个模块、其中 15 个含浏览器 API。**跨端复用的单位不是 api 文件，是「api + store + 存储适配」整层**——存储适配层是所有页面共享的前置底座，必须先做。

## 2. 四级分级落位

### 2.1 分级判据（先立规则，再落页）

| 级别 | 判据 | 决策含义 |
|---|---|---|
| **P0** | 员工**每天**都做、动作闭环（查→改→提交）能 3 屏内完成；失败可重试、不产生不可逆后果 | 首版必须进，缺一版不能上线 |
| **P1** | **周频**，或「低频但每天可能被问到」；读为主、写为辅 | 二期进，首版可用 H5/桌面兜底 |
| **P2** | **低频只读**，只有查看价值 | 可延后，甚至永久留在桌面 |
| **NO-GO** | **不该**进：不可逆破坏性、权限/密钥中枢、涉敏个人信息、或纯桌面工作流 | 明确不做，**不是「做不了」** |

**关键原则**：NO-GO 的判定依据是**「为什么不该进」**（后果、权限、场景），不是技术难度。技术上 2,621 行的会员管理能重写，673 行的备份页同样能重写——但备份页放手机上是**风险决策**，不是工程决策。

### 2.7 单列：marketing（朋友圈 / 小红书 / 防折叠 / 谈单）到底归哪一桶

**落位：`marketing/*` 4 文件 3,327 行归 P1，不是 NO-GO。但「怎么进」要按动作拆，不能整页平移。**

captain 的倾向（「产物生成可进小程序、富文本编辑留 web」）**方向对，但理由在本仓库不成立**——实测 `views/yimai/marketing/` 下 **零富文本**：`grep -rn "WangEditor|wangeditor|ArtWangEditor|contenteditable|innerHTML"` → **0 命中**；`wangEditor` 只存在于 `components/core/forms/art-wang-editor/index.vue`，**业务页从未挂载它**。文案编辑用的是纯 textarea：`moments-tool.vue:520,522`、`xhs-tool.vue:491,495`、`anti-fold-tool.vue:112`（均 `ElInput type="textarea" :rows="8"`）。所以「wangEditor 不支持移动端」这条约束**不作用于 marketing**。

真正的手机端约束是另外两条，以及一条**反向支持**：

| 维度 | 实测 | 对小程序的影响 |
|---|---|---|
| 长文精修效率 | 正文按 1000+ 字生成，`:rows="8"` 在 375px 下约显示 10 行 | ⚠️ 逐字改写不划算 → **精修留 web** |
| 图片配图 | `moments-tool` 有 `ElUpload×1`（配图 ≤3 张，`MOMENTS_MAX_IMAGES`） | ⚠️ 需换 `wx.chooseMedia` + `wx.uploadFile` |
| **产物落地** | 全页布满「复制」动作：`xhs-tool.vue:320`（复制封面）/`:355`（复制回复）/`:376`（复制整篇）/`:475,587`（复制这段/复制正文）/`:534-542`（更多菜单里的复制正文/封面/首评）；`moment-tool` 同构 | ✅ **这是手机端最顺的动作**：`wx.setClipboardData` + `wx.saveImageToPhotosAlbum` 一步到位，比在电脑上复制再发微信更短 |

**结论（可写进方案的措辞）**：marketing 的正确切法是 **「生成 + 一键复制/存图」进小程序，「逐字精修」留 web**——分界线是**动作**（生产 vs 精修），不是**页面**。理由不是富文本（本页没有富文本），而是「长文编辑的屏效」+「配图上传换 API」；而「复制到剪贴板/相册」这条反而是小程序相对 web 的**净优势**，因为没有 `navigator.clipboard` 的授权弹窗摩擦。

> 边界建议给 `optimizer`：marketing 进小程序时用**原生页**（生成 + 复制 + 存图），**不要**用 `web-view` 包整页——`web-view` 里 `navigator.clipboard` 在 iOS 微信内不可靠，恰好会废掉这个模块最有价值的那一步。

### 6.2 为什么这是「先决条件」而不是「顺手改」

`api/yimai.ts` 里 `USE_BACKEND` 字样 51 处、**正向 `if (USE_BACKEND)` 分支 36 个**，HTTP 分支正文合计 **292 行**，占该文件 **7.3%**（§8-C12）；其余 92.7% 是**走 `useYimaiStore()` 的本地演示数据层**。

> **口径修正（captain 核验后修订）**：初版写的「26 个 `if (USE_BACKEND) {…}` 块 / 277 行 / 7.0%」是**只统计带花括号的块**（`grep -c "if (USE_BACKEND) {"` = 26）。完整口径是 **36 个正向分支** = 26 个带花括号块 + **7 个单行**（如 `if (USE_BACKEND) return apiGet('/today/summary')`）+ **3 个条件与语句分行且无花括号**（`:1399`、`:3796`、`:3923`）；另有 8 个 `if (!USE_BACKEND)` 反向分支不计入上线路径。行数随之 277 → **292**，占比 7.0% → **7.3%**。captain 的 `grep -cE "if\s*\(\s*USE_BACKEND"` = 36 正确，我的 26 是更窄的「仅花括号块」模式。

> **在 demo 模式下，`api/yimai.ts` 的数据来源就是 pinia store；而 pinia store 的持久化介质是 `localStorage`。**
> 换句话说：**api 层 → store 层 → localStorage 串在一条链上**，任何一段在小程序里不存在，整条链断。

> 顺带一个对迁移有利的事实：`.env.production` 里 `VITE_USE_BACKEND = true`（`admin-web/.env.production`），**上线路径只走那 292 行 HTTP 分支**，3,600 行 demo 层是可选资产（小程序若不做 demo 模式可以不搬）。
