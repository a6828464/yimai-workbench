## 1 对基线卡的校准（7 处：1.1–1.5 数字/事实，1.6 口径，1.7 合规）

### 1.1 包体上限：不只"主包 2MB / 总包 20MB"

| 事实 | 锚点 |
|---|---|
| 「整个小程序所有分包大小不超过 **30M**（服务商代开发的小程序不超过 **20M**）」 | https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages.html（抓取 2026-11-03） |
| 「单个分包/主包大小不能超过 **2M**」 ⏳ | 同上 |
| 参照：`subPackages` 配置路径外的目录**全部**打进主包；tabBar 页面**必须**在主包内 | https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages/basic.html（抓取 2026-11-03） |

**修正**：00 卡 C1 记的"总包 20MB"是**服务商代开发**口径。一麦自建小程序总包上限是 **30MB**，主包仍 2MB。
**未核实**：2MB 是压缩前还是压缩后口径，官方正文未写。→ 列为 M1 退出条件（用开发者工具「详情→本地代码→代码包大小」实测，见 §6 M1）。

### 1.2 SSE：不是"完全不行"，是"要自己拆帧"

| 事实 | 锚点 |
|---|---|
| `wx.request` 参数 `enableChunked`（boolean，默认 false）「开启 transfer-encoding chunked」，基础库 **2.20.2** 起 | https://developers.weixin.qq.com/miniprogram/dev/api/network/request/wx.request.html（抓取 2026-11-03） |
| `RequestTask.onChunkReceived`「监听 Transfer-Encoding Chunk Received 事件」，`data` 为 **ArrayBuffer**，基础库 **2.20.1** 起 ⏳ | https://developers.weixin.qq.com/miniprogram/dev/api/network/request/RequestTask.onChunkReceived.html（抓取 2026-11-03） |
| 后端实现：`response()->stream()` + `text/event-stream` + `X-Accel-Buffering: no`，逐 1KB 转发上游 | `backend/app/Http/Controllers/AiController.php:161,182` |
| 路由：`POST /api/ai/chat`，`throttle:30,1` | `backend/routes/api.php:123` |

**修正**：00 卡把 SSE 记为"wx.request 不支持流式读取"。准确表述是：**没有 EventSource，但有 chunked 通道**。AI 流式在小程序侧可行，代价是要自己实现 event-stream 拆帧（`data:` / `\n\n` 边界 + UTF-8 多字节跨 chunk 拼接），且 nginx 不能对 `/api/ai/chat` 开 gzip。→ 归入 **P1**（不在 P0 阻塞项），方案见 §4.3。

### 1.6 口径校准：Element Plus 的 grep 陷阱与我的复现（v1.1 新增）

**反向验证（已知为真的样本）**：

| 检查 | 结果 | 含义 |
|---|---|---|
| `grep -rhoE "<el-[a-z-]+" src` | **9 处** | 全部落在 **JSDoc 注释里的用法示例**：`src/directives/core/roles.ts:19,22`、`src/directives/core/auth.ts:17,20,23`、`src/directives/business/ripple.ts:20,23`、`src/hooks/core/useAuth.ts:25,26` —— **真实模板 0 处** |

### 1.7 合规前提（v1.1 新增，**推翻本文档 v1.0 的一处前提**）

#### 1.7.1 微信授权登录：从"P1 优化"上调为 **P0/M1 必交付**

| 事实 | 锚点 |
|---|---|
| 《微信小程序平台运营规范》**2.12 技术实现规范 第 6 条 授权登录**：「**微信小程序内存在账号体系时，必须提供微信授权登录**。」同条另要求：拒绝授权后可在用户表现出意向时再提醒；应提供「功能正常且易于发现的『退出』选项」；用户拒绝授权后须清除并不再使用其微信头像/昵称等数据 | https://developers.weixin.qq.com/miniprogram/product/（抓取 2026-11-03） |

**影响**：一麦工作台**必然**存在账号体系（136 条路由、25 个控制器、Sanctum 账号密码登录）→ **只保留 Bearer 账号密码登录 = 不合规**。

**最小改造量（事实核查结论，供 `be-analyst` 对齐）**：

| 项 | 现状 | 锚点 |
|---|---|---|
| users 表有无 `openid`/`unionid` | **都没有**（只有 `name/password` 等，见迁移） | `backend/database/migrations/0001_01_01_000000_create_users_table.php:19`、`backend/app/Models/User.php:17-31`（`fillable` 无 openid） |
| token 签发 | `$user->createToken('workbench')->plainTextToken`，14 天 | `backend/app/Http/Controllers/AuthController.php:35`、`backend/config/sanctum.php:53` |
| `code2session` 端点 | **不存在**（00 卡 §6 空白 3） | `backend/routes/api.php` 无对应路由 |

→ 需新增：`openid`（+可选 `unionid`）字段与唯一索引、`POST /api/auth/wechat`（`code` → `jscode2session` → `openid` → 查/绑用户 → **仍签发 Sanctum Token**）。**Sanctum 机制不变**，只换/加登录入口 —— 这是"合规成本可控"的关键。

→ 因此本文档 v1.0 §4.3「账号密码登录，`code2session` 列 P1」**已作废**，改为：**M1-2 必须闭环微信授权登录**（原账号密码作为绑定/兜底入口，二者共用同一 token 机制）。

#### 1.7.2 预付卡：小程序内**不开放任何收款**

| 事实 | 锚点 |
|---|---|
| 类目「预付卡（发行方）」资质 2 选 1：①《单用途预付卡》**备案公示材料**；②《支付业务许可证》（含预付卡业务 / 储值账户运营Ⅱ类）。适用范围：「服务中含有在线销售具有预充值凭证卡、**会员卡预充值**、储值卡购买等功能类服务」 | https://developers.weixin.qq.com/miniprogram/product/material/（抓取 2026-11-03） |
| 《单用途商业预付卡管理办法（试行）》**第十八条**：单张记名卡限额不得超过 **5000 元**，单张不记名卡限额不得超过 **1000 元** | https://www.mofcom.gov.cn/zfxxgk/zc/gz/art/2021/art_82805c1937a64a4186ea15c23fc675c5.html（商务部，抓取 2026-11-03） |
| **第十九条**：**记名卡不得设有效期**；不记名卡有效期不得少于 3 年 | 同上 |

**结论（写死）**：会员卡/课时包属预付卡，一麦作为小型场馆**拿不到备案公示材料**（也未持支付牌照）→ **小程序内不开放收款**：不出现价格、不出现"立即购买/续费/充值"按钮、不接微信支付。任何涉及收款的入口一律**留在 web/H5 或线下**。这条同时影响 §4.2（不做清单）、§6（M3 验收）、§7（风险登记）。

## 2 六条候选路线逐条对比

> **维度说明**：A/B/C 是**框架维度**，D/E 是**容器维度**，F 是**范围维度**。按要求把 F 独立成条，但它与 A/B/C 正交 —— 实际选型是 `F × (A|B|C)` 的组合，见 §2.7。

### 2.0 四个依赖的"死亡判定"总表（所有路线的共同前提）

| 依赖 | 本仓库事实（锚点） | 小程序里能不能跑 | 依据 |
|---|---|---|---|
| **Element Plus 2.11** | `admin-web/package.json:67`；实测 **≈2,400 处**标签 / **57 种**组件（精确 2,408/58 全 `src`，见 §1.6）、`ElMessage` **315 处**（精确 302 处，见 §1.6）、`ElMessageBox` 22、`v-loading` 78、`ElTable` 41、`ElDialog` 34、`ElDrawer` 17、`ElDatePicker` 16 | **❌ 任何路线都不能** | 小程序逻辑层「**并不能直接使用 DOM API 和 BOM API**……jQuery、Zepto 等在小程序中是无法运行的；一些 NPM 的包在小程序中也是无法运行的」— https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/（抓取 2026-11-03）。Element Plus 是 DOM 组件库（Popper/Teleport/ResizeObserver 全套） |
| **Tailwind 4.1** | `admin-web/package.json:59,76`；`@import 'tailwindcss'` + `@theme` + `@custom-variant`（`admin-web/src/assets/styles/core/tailwind.css:1-2`）；无 `tailwind.config.js`；87/136 个 `.vue` 的 `class="..."` 里出现工具类前缀（粗略 grep：`flex|grid|gap-|px-|py-|text-sm|font-`，偏低估） | **⚠️ 路线相关**：D 原样可用；A/B/C 必须加 `weapp-tailwindcss` 补丁 | ① WXSS「属性名选择器 `[...]` 不会生效；不支持带参数的伪类和伪元素选择器」— https://developers.weixin.qq.com/miniprogram/dev/framework/view/wxss.html（抓取 2026-11-03）。② 自定义组件内「不能使用 id / 属性 / 标签名选择器」— https://docs.taro.qq.com/docs/react/component-style（源自 `NervJS/taro-docs/docs/component-style.md`，抓取 2026-11-03）。③ Taro 官方指南明确要求装 `weapp-tailwindcss` + `weapp-tw patch`，且示例为 **Tailwind 3.x + postcss**，未覆盖 4.x CSS-first — 同 docs 站 `tailwindcss` 页（抓取 2026-11-03） |

**这四行是全文档的核心**：Element Plus 与 wangEditor 是**淘汰项**（必须换/留在 web），Tailwind 是**补丁项**，ECharts 是**换接入方式**。任何"全量迁移"的承诺都必须先解释这四行怎么过。

### 2.1 路线 A：原生微信小程序（WXML/WXSS/TS）

| 项 | 结论 |
|---|---|
| 形态 | 纯原生：`app.json` + WXML/WXSS/TS，无框架运行时 |
| **Element Plus** | ❌ 不可用。替代：`@vant/weapp` 1.11.7（npm 全量安装 868.4 KB，按需只引用的组件）或原生 `view/text/button` 自建 |
| **Tailwind** | ⚠️ 需 `weapp-tailwindcss` 5.6.3 的**原生小程序**入口（postcss/gulp 插件）；Tailwind 4 CSS-first 用法需自行验证 |
| **ECharts** | ✅ `ec-canvas` 是为此场景设计的（原生组件，直接 `usingComponents`） |
| **wangEditor** | ❌ 换成 `<textarea>` + 服务端富文本，或编辑器留在 web |
| **MobileCard 设计复用** | ✅ **最高**。6 个属性（title/subtitle/tags/metrics/note/actions）+ 3 个插槽，用 `wxml` 的 `slot` 1:1 复刻，无框架阻抗 |
| **主包 2MB 压力** | ✅ **最低**。无 Taro/uni 运行时；主包 = 骨架 + tabBar 4 页 + vant 按需 ≈ 200–400KB（【估算】，需 M1 实测）。可以把 P0 六页全塞主包，甚至不需要分包 |
| **学习成本** | ❌ **最高**。团队是 Vue3 心智（`defineProps`/`computed`/`Pinia`）；WXML 表达式能力弱（无 `computed`、无 `filter`）、`setData` 手动 diff、无 `.vue` 单文件、无 npm 生态直用 |
| **长期维护** | ⚠️ 双栈并行（web 用 Vue，小程序用 WXML）→ **两套组件、两套状态、两份 bug**。136 个 `.vue` 业务逻辑无法共享（连 `api/` 层都要重写一遍 `Taro.request` → `wx.request`） |
| **双锚点** | 仓库：`admin-web/src/components/business/mobile-card/index.vue:105-121`（要复刻的 props 契约）；外部：https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/code.html（代码构成）、https://developers.weixin.qq.com/miniprogram/dev/framework/view/wxss.html（抓取 2026-11-03） |

**一句话**：体积与性能最优，**人力成本最贵**，与现技术栈零复用。适合"重写一个只读的轻应用"，不适合"从 27,911 行 Vue 里切子集"。

### 2.2 路线 B：Taro 4（Vue3）

| 项 | 结论 |
|---|---|
| 形态 | Taro `4.3.2`（`@tarojs/cli` npm latest，2026-11-03）编译到微信小程序；写 Vue3 SFC，`@tarojs/components` 提供 `View/Text/Input` 等跨端组件 |
| **Element Plus** | ❌ 不可用。替代：**NutUI（Vue3，京东官方，Taro 推荐模板）** 或 `@vant/weapp`（需 `usingComponents` 引原生组件，会牺牲多端转换能力） |
| **Tailwind** | ⚠️ **官方指南存在**（价值最高的证据）：Tailwind 3.x + postcss + `preflight:false` + `weapp-tailwindcss` 的 `UnifiedWebpackPluginV5` + `rem2rpx`。Tailwind **4.x CSS-first 不在该指南覆盖内** → 本项目 Tailwind 4 要么降级配置形态、要么自证（M1 的验证项之一） |
| **ECharts** | ✅ 通过 `usingComponents` 引 `ec-canvas` 原生组件（Taro 官方文档 `hybrid.mdx` 的示例**就是 ec-canvas**）。注意：引用原生组件后该项目**不再具备多端转换能力** —— 对"只投微信"的一麦无损失 |
| **wangEditor** | ❌ 同 A |
| **MobileCard 设计复用** | ✅ 高。`<View class="mobile-card__head">` 直接照搬 BEM 类名；`ElTag` → NutUI `Tag` 或 `view` 自绘；props 契约可原样保留（TS 类型可直接复制 `mobile-card/types.ts`） |
| **主包 2MB 压力** | ⚠️ 中。Taro 4 是**运行时驱动**（官方自述与 Kbone 同思路，用运行时渲染器），runtime 有固定成本：`@tarojs/taro` 4.3.2 npm 解包 1,250 KB（源码口径），**编译后 gzip 估算 150–350KB**（【估算】）。主包 = Taro runtime + Vue3 runtime（现 H5 实测 `vue-vendor` 48KB gz）+ NutUI 按需 + 6 页业务 ≈ **0.7–1.1MB gz**（【估算】）。ECharts 必须进**独立分包或分包异步化** |
| **学习成本** | ✅ **低**。Vue3 SFC + `script setup` + Composition API + Pinia（Taro 官方有 `pinia.md`）+ TS，与现仓库 `admin-web/src/store`、`api/` 写法同构；`admin-web/src/views/**` 的 `<script setup>` 逻辑块可**整段搬运**，只改模板标签与 API 调用 |
| **长期维护** | ✅ 单栈（Vue3 + TS），web 与小程序共享 `types/`、`api/` 的请求契约、`utils/` 纯函数；组件两套（web=EP，小程序=NutUI），但**业务逻辑一套** |
| **已知坑（官方文档明写）** | ① 小程序**不支持 `<style scoped>`**，建议换 CSS Modules → 现仓库 **43/136** 个 `.vue` 用了 `<style scoped>`（其中 views 31 个），子集内仍需逐个改；② 不支持应用级 `<teleport>`；③ `Picker` 等小程序特有表单**不兼容 `v-model`**；④ Vue3 基于 Proxy，iOS9 及以下不可用 |
| **双锚点** | 仓库：`admin-web/src/views/yimai/today/index.vue:21-25`（角色分流，P0 入口）、`admin-web/src/components/business/mobile-card/types.ts`（可直搬的类型）；外部：`NervJS/taro-docs/docs/vue3.md`（抓取 2026-11-03，对应 https://docs.taro.qq.com/docs/vue3/index.html）、`docs/tailwindcss.mdx`、`docs/hybrid.mdx`、`docs/pinia.md` |

**一句话**：**技术栈同源、子集可切、生态有一手文档背书**。代价是多一层构建链与运行时体积。

| **双锚点** | 仓库：`admin-web/package.json:77`（vue 3.5.21，语法可平移）；外部：https://uniapp.dcloud.net.cn/tutorial/vue3-basics.html（抓取 2026-11-03） |

**一句话**：与 B 同档，**工程纪律契合度低于 B**（HBuilderX 主线 vs 现有 pnpm/vite 流水线），多端能力用不上。若团队更熟 uni-app，切 C 的代价很小 —— 这也是 §5 反方 B 的立论。

### 2.4 路线 D：web-view 套壳现有 H5

| 项 | 结论 |
|---|---|
| 形态 | 小程序只做「登录页 + 一个 `web-view` 指向现 `admin-web` 的移动端路由」；业务零改动 |
| **Element Plus** | ✅ **原样可跑**（跑在 WebView 里，是浏览器环境）。`ElTable` 在 ≤768px 已降级为 `MobileCard` 卡片列表（`admin-web/src/config/breakpoints.ts:32-42`） |
| **Tailwind** | ✅ 原样可用。⚠️ 但 Tailwind 4 的浏览器基线是 **Safari 16.4 / Chrome 111 / Firefox 128**（https://tailwindcss.com/docs/compatibility，抓取 2026-11-03）；微信内嵌 XWeb 的 Chromium 版本必须 M1 实机验证（官方仅说明「基于 Mobile Chromium 内核」，未给版本号 — https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/env.html，抓取 2026-11-03） |
| **ECharts** | ✅ 原样可用（Canvas/DOM 皆在 WebView 内） |
| **wangEditor** | ⚠️ 能加载但**官方明示不支持移动端编辑**，手机上等于只读 → 编辑功能仍不可用（与路线无关，是库本身的限制） |
| **MobileCard 设计复用** | ✅ 100%（就是原代码）。这是 D 的杀手锏：15 页 + 10 模块的窄屏卡片已经实测通过（00 卡 §3） |
| **主包 2MB 压力** | ✅ **零压力**。主包只有壳页（<50KB）；H5 资源在服务端，不受小程序包体限制；代价是**首屏要下 H5 资源**（现全站 gz 1.19MB，但按路由懒加载，首页实际只需 657KB 骨架 + 当页 chunk） |
| **硬限制（官方）** | ① **个人类型小程序不支持 web-view**；② 网页「需登录小程序管理后台配置**业务域名**」；③ 业务域名必须 **HTTPS + ICP 备案**，「新备案域名需 24 小时后才可配置」；④ 每账号最多 300 个域名；⑤ 「小程序插件中不能使用」；⑥ web-view 内只能用 JSSDK 的**有限子集**（`navigateTo/redirectTo/switchTab/reLaunch/navigateBack/postMessage/getEnv`…）；⑦ **v1.1 补充**：web-view 里打开的 H5 **仍属"小程序内提供的服务"** → 若该 H5 含会员卡充值/课时包收款，同样触发「预付卡」类目要求（§1.7.2）。**所以"支付留 web" 必须指"小程序之外打开的 web"，不是 web-view 内嵌页。** |
| **学习成本** | ✅ **最低**（近乎零）。改造成本 = 1 个壳页 + 业务域名配置 |
| **长期维护** | ⚠️ 双容器体验：小程序导航栏 + WebView 滚动条；**分享卡片/订阅消息/微信登录**都要靠 JSSDK 桥接，能力残缺；审核对"纯套壳"敏感（本项**待核实**，见 §7 R4） |
| **双锚点** | 仓库：`admin-web/src/router/index.ts:10`（hash 路由，web-view 里天然兼容 `#/yimai/today`）、`admin-web/.env.production`（同域 `/api` 反代，省一次跨域）；外部：https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html、https://developers.weixin.qq.com/miniprogram/dev/framework/ability/domain.html（抓取 2026-11-03） |

**一句话**：**验证成本最低、能力上限也最低**。它是 M0 的并行探路器与 fallback，不是终局（理由见 §5 反方 A 的回应）。

### 2.5 路线 E：混合（原生/Taro 壳 + web-view 局部嵌入）

| 项 | 结论 |
|---|---|
| 形态 | 原生/Taro 实现 tabBar 四页（工作台/待办/我的/…），**重后台操作**（薪酬、备份、系统日志、AI 配置）用 `web-view` 打开现 H5 对应路由 |
| **Element Plus** | ⚠️ 分治：壳页用 NutUI/vant；web-view 页用 Element Plus。**两套 UI 并存**，视觉一致性靠设计规范约束，不靠代码 |
| **Tailwind** | ⚠️ 分治：壳页需补丁，web-view 页原样 |
| **ECharts** | ⚠️ 分治：壳页 `ec-canvas`，web-view 页原 ECharts |
| **wangEditor** | ⚠️ 只能在 web-view 页用（且移动端编辑不可用）→ 结论：**编辑器相关功能留桌面端** |
| **MobileCard 设计复用** | ✅ 壳页复刻设计；web-view 页直接复用代码 |
| **主包 2MB 压力** | ✅ 低（同 A/B，web-view 页不占包体） |
| **最大风险** | 「**双层导航 + 双份登录态**」：WebView 与小程序的 token 需要桥接（`postMessage` 只在后退/销毁/分享/复制链接时触发 → 见 web-view 文档 `bind:message` 触发时机），登录态同步要做 URL 传参或 `wx.miniProgram.postMessage` 回传 |
| **学习成本** | ❌ **最高**（三套心智：壳框架 + WebView 桥 + 两套 UI） |
| **长期维护** | ❌ 最差。两套 UI 各自演化，桥接层是永久负债；一旦 H5 路由变化，小程序侧无感 break |
| **双锚点** | 仓库：`admin-web/src/router/routes/staticRoutes.ts:34-50`（`/s/:code` 等公开分享页，天然适合 web-view 或原生页）、`admin-web/src/views/yimai/today/index.vue:21-25`（角色分流，壳页按角色决定要不要给 web-view 入口）；外部：web-view 文档同上；Taro 引原生组件 `docs/hybrid.mdx` |

**一句话**：**过渡期最优、终局最差**。建议只在 P1/P2 阶段作为"低频后台功能"的逃生舱，不作为架构主干。

### 2.6 路线 F：精选子集迁移（独立路线，范围维度）

> 题面要求单独评估，这里把它当**独立路线**而不是"某框架的选项"。

| 项 | 结论 |
|---|---|
| 形态 | 不是框架，是**范围决策**：从 136 个 `.vue` / 27,911 行里切出 P0 子集进小程序，其余 **永久留在 web**。可与 A/B/C 任意组合 |
| **判定标准（可验收）** | 一个页面进小程序，必须同时满足 **5 条**：① 手机竖屏单手可完成（无需宽表/多列对比）；② 触控目标 ≥44px；③ 不依赖 wangEditor 富文本编辑；④ 不依赖文件上传/下载或本地文件系统；⑤ **不含任何收款/充值/价格诱导入口**（§1.7.2）。**豁免项**：登录页无条件 P0（合规要求，§1.7.1） |

## 3 【关键章节】全量迁移 vs 精选子集迁移

### 3.1 全量迁移：不是"难"，是**数学上不成立**

| 证据 | 数字 | 锚点 |
|---|---|---|
| 需改写的页面 | 136 个 `.vue` / 27,911 行（views） | 00 卡 §2 |
| 需替换的 Element Plus 触点 | **2,400 处**标签 / **56 种**组件 / 302 处 `ElMessage` / 78 处 `v-loading` / 22 处 `ElMessageBox` | 本次实测 |
| 需处理的 `scoped`（Taro 不支持） | **43** 个 `.vue`（views 31 个） | 本次实测 + `docs/vue3.md` |
| 必须留在 web 的能力 | wangEditor（移动端编辑不可用）、备份上传下载、xlsx 薪酬导入、日志下载 | `art-wang-editor/index.vue:21-26`、`backend/app/Http/Controllers/BackupController.php:213`、`PayrollController.php:363` |
| 结论 | 全量 = 把 2,400 处 DOM 组件 + 全部宽表交互重写成小程序组件 → **等于重写前端，且把桌面端独有能力硬塞进手机** |

**另一个反直觉点**：全量迁移的**体积**是够的（1.19MB gz < 2MB），但**能力**不够 —— 2MB 从来不是主要矛盾。真正不可迁的是交互范式（`ElTable` 固定列、`ElDialog` 模态、批量选择、键盘快捷键），这些在手机上本来就是坏的，搬过去只会把 web 的债搬进手机。

### 3.2 子集迁移：切分口径（可验收，不是感觉）

**四条硬判据**（任一不满足即留 web）：

1. **单手竖屏可完成** —— 是否需要并排对比 ≥3 列数据？（是 → 留 web）
2. **触控目标 ≥44px** —— `TOUCH_TARGET_MIN = 44`（`admin-web/src/config/breakpoints.ts:42`），桌面端 ≤28px 的行内按钮在手机上全部要重排
3. **不含富文本编辑** —— wangEditor 官方不支持移动端编辑
4. **不含文件上传/下载** —— 备份恢复、xlsx 导入、日志下载

**角色维度**（`admin-web/src/views/yimai/today/index.vue:21-25` 已实现四级分流）：

| 角色 | 移动端真实场景 | 进小程序 |
|---|---|---|
| `R_TEACHER` / `R_SERVICE` | 站着上课前看课表、课后填分析、看自己 KPI | ✅ **P0 主战场** |
| `R_MANAGER` | 巡店看数据、审批 | ⚠️ P1（审批进，看板留 web） |
| `R_SUPER`（老板） | 看汇总、看薪酬 | ⚠️ 老板看板 P2；薪酬/备份留 web |
| `R_MEDIA`（新媒体） | 写文案、发朋友圈 | ⚠️ P1（有 2,418 行差距规格） |

### 3.3 子集的两条实施口径（必须二选一，不能模糊）

| 口径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **口径 1：新建仓**（推荐） | 新建 `miniapp/`，从 `admin-web` **复制** P0 六页的 `<script setup>` 逻辑块 + `api/` + `types/`，模板重写 | 不污染 web 构建；小程序可用不同构建配置；web 零回归风险 | 逻辑块有**复制性重复**（同一 bug 修两遍） |
| 口径 2：单仓多端 | 把 `api/`、`types/`、`utils/` 提成 workspace 包，web 与小程序共用 | 无重复 | 需先做包拆分（`admin-web` 现在是单体），改造成本前置 |

**建议**：M1 用口径 1 快速验证；**只有确认长期双端并行**（P1/P2 全做）才投入口径 2。理由：口径 2 的包拆分本身是 2–3 周的架构改造，在可行性未验证前投入是赌博。

## 4 推荐路线

### 4.1 选型结论

> **F × B：精选子集（F）+ Taro 4 / Vue3（B）+ `ec-canvas` 原生图表；D（web-view 套壳）作为 M0 并行探路与 fallback。**

组合理由（按权重）：

1. **人才与心智复用**（权重最高）：现仓库是 Vue3 + TS + `<script setup>` + Pinia（`admin-web/package.json:77`、`src/main.ts:1-30`、`src/store`）。Taro 4 支持 Vue3（`docs/vue3.md`），P0 六页的逻辑块可整段搬运，只重写模板。原生方案（A）要重学 WXML 表达式与 `setData`，ROI 最低。
2. **子集让"框架税"变得可承受**：P0 只有 4,515 行（全站 16%），页面级 chunk 估算 30–60KB gz → 主包预算留给 runtime 与组件库。
3. **ECharts 有官方逃生舱**：`ec-canvas` 是 ECharts 官方团队的微信适配，Taro 官方 `hybrid.mdx` 的示例之一就是它 → 图表不需要自研。
4. **可证伪**：M1 有明确的"切 C/A"的量化条件（§0、§6），选错可以在 2 周内止损。
5. **fallback 已在手**：D 路线 1–2 周可出内测版；若 M1 发现 Taro 体积/性能不达标，直接降级到 D，项目不归零。

## 5 反方意见（不粉饰，逐条正面回应）

### 反方 A：「纯 web-view 套壳就够了，你要的只是手机上能看」

**立论强度：★★★★☆（最强的一条）**

论据：
- 一麦**已经**有验证过的移动端：15 页 + 10 模块的窄屏卡片降级、44px 触控、抽屉侧栏，23 项基线失败清零（00 卡 §3）。
- hash 路由（`admin-web/src/router/index.ts:10`）在 web-view 里天然可用，`#/yimai/today` 直接落地。
- 同域 `/api` 反代省掉跨域与域名白名单的复杂度。
- 1–2 周可上线，Taro 方案要 4–5 周。
- 主包零压力。

**我的回应（为什么不选 D 作终局）**：
1. **能力残缺不是"少一点"，是结构性缺失**：web-view 内只能用 JSSDK 有限子集（`navigateTo/redirectTo/switchTab/reLaunch/navigateBack/postMessage/getEnv`）—— https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html。**订阅消息、微信分享卡片（自定义标题/图片）、`wx.login`、扫码、`chooseImage`** 都不在列。
2. **`postMessage` 的触发时机受限**：只在「小程序后退、组件销毁、分享、复制链接」时触发（同上文档）→ 无法做实时双向桥；登录态同步只能靠 URL 传参（token 进 URL 是安全事故面）。
3. **双层体验**：小程序导航栏 + WebView 自身滚动/加载，首屏是"白屏 → H5 骨架 → 内容"三段式。
4. **审核不确定性**：纯套壳被判定"无实质内容/诱导下载"的风险无法用文档消除（本项标【待核实】，见 §7 R4）。

**但 A 成立的条件必须写清**：如果 YG 的目标是"**一周内让老师能在手机上用**"，**D 是唯一正确选择**，且它不阻塞 B —— 先上 D，再并行做 B。**这也是我在 M0 里把 D 列为并行探路的原因**。

### 反方 B：「uni-app 比 Taro 更合适，你选 Taro 是因为你会 Taro」

**立论强度：★★★★☆**

论据：
- 一麦只投微信 → Taro 的"多端转换能力"是空转溢价；而 Taro 3+ 是**运行时驱动**（官方自述「Kbone 内部实现了轻量级的 DOM 和 BOM API……Taro Next 也有着同样的思路」— `NervJS/taro-docs/docs/difference-to-others.md`），运行时必然比编译式更重、首屏更慢。
- uni-app 中文生态、文档、插件市场更贴近"一个人接私活"的场景；Vue3 支持明确（`https://uniapp.dcloud.net.cn/tutorial/vue3-basics.html`）。
- Taro 4 的 Tailwind 官方指南仍停留在 **Tailwind 3.x + postcss**，而一麦是 **Tailwind 4 CSS-first**（`admin-web/src/assets/styles/core/tailwind.css:1-2`）→ "官方指南"这层优势对一麦**部分失效**。
- Taro 版本迭代快（`@tarojs/cli` 4.3.2），升级破坏面大。

**我的回应**：
1. **认输的部分**：反方成立。Taro 的运行时体积优势确实不如编译式（见 §2.2 的 150–350KB 估算），Tailwind 4 的指南落空也是真的。**所以我在 §0 给了可证伪条件**：M1 若实测主包 gz > 1.2MB 或 tabBar 首屏 > 2.5s，**立即切 C（uni-app）**，不改范围、不改 P0 清单 —— 因为 F 是范围策略，与框架正交。
2. **不让步的部分**：uni-app 的主线工具是 HBuilderX，与本仓库 `pnpm + vite7 + vue-tsc + eslint9 + husky + lint-staged`（`admin-web/package.json:9-23`）的工程纪律冲突；且 `@dcloudio/uni-app` 的版本号形态（`2.0.2-5030320261023001`）说明其发版节奏与语义化版本无关，**升级预期更难管理**。
3. **诚实的结论**：B 与 C 的实际差距 < 1 周工作量，**这是"选哪个都不算错"的地带**。决定权应交给"谁维护"：若由熟悉 Vue 工程化的人维护 → B；若由更熟 uni-app/HBuilderX 的人维护 → C。

### 反方 C：「这个项目根本不该做」

**立论强度：★★★☆☆（但杀伤力最大）**

论据：
- P0 六页的移动端形态**已经存在**（MobileCard + 44px + 抽屉），老师今天用手机浏览器打开就能用。
- 小程序带来三条**净增量**：① 微信内分享卡片（课后分析/训练计划发给会员）；② 订阅消息（上课提醒）；③ 免登录（`wx.login` 静默）。
- 若这三条都不做，小程序的唯一收益是"入口在微信里更好找"—— 而这个收益抵不过 4–5 周 + 长期双端维护 + 每年类目/审核/合规复核。

**我的回应**：
1. 这条反方**部分成立**，它决定了**是否立项**，而不是**选什么框架**。→ 我把它前置成 **M0 的 Go/No-Go 判据**（§6）：**三条净增量里至少两条能在 M0 写出验收口径，否则不立项**。
2. 特别提醒：**订阅消息**需要用户主动订阅（一次性/长期），且模板需审核；**分享卡片**需要 `onShareAppMessage` + 页面路径规划 —— 这两条都是**产品设计工作量**，不是技术选型能解决的。
3. 若三条净增量只有一条成立 → 选 **D（web-view套壳）**，把项目压缩到 2 周内，不做 Taro。
