## 0 一句话判定

**有条件可行。** 但「把前端迁移一份」这个说法本身需要修正——

**不是「把前端搬到小程序」，而是「为员工高频动作新做一个 7 页的小程序」**，因为 Element Plus 在小程序里一行都跑不了（`<El*` 实测 **2,401 处 / 57 种组件**、`ElMessage` 315 处、`v-loading` 78 处）。全量迁移等于重写整个 UI 层，**数学上不成立**。

**三个前提条件**，任一不满足则不要开工：

| # | 前提 | 现状 | 卡点等级 |
|---|---|---|---|
| P1 | **域名备案主体与小程序主体一致** | ❌ **未确认**：`DEPLOY.md` 无备案号记录，工信部查询需验证码无法程序化取信 | 🔴 硬门（全链路最慢一环，1–20 天） |
| P2 | **必须提供微信授权登录** | ❌ 未实现：运营规范 2.12.6 要求「存在账号体系时必须提供微信授权登录」，现有纯账号密码**不合规** | 🔴 硬门（后端 1.5 人日） |
| P3 | **服务器域名白名单三件套** | ⚠️ 域名 HTTPS 已通（Let's Encrypt，有效至 2027-01-26），但白名单未配 | 🟡 运维动作，非代码 |

## 1 推荐路线（采纳 `architect` 的 F+B）

| 维度 | 结论 |
|---|---|
| **范围策略** | **F = 精选子集**：只做 7 页，其余留 web。**不做全量。** |
| **框架** | **B = Taro 4（Vue3）**：能复用现有 Vue3 语法习惯与 `<script setup>` 逻辑块 |
| **图表** | 原生 `ec-canvas` 嵌入；**P1 看板先只做数字卡 + 服务端出图**（见 §5 风险 R3） |
| **并行探路** | **D = web-view 套壳**：1–2 周出可用内测版，作为 M0 的 fallback，**不是终局** |
| **P0 七页** | 登录（含微信授权）/ 我的工作台 / 今日待办 / 课后分析 / 训练计划 / 任务 / 审批 —— 面向 `R_TEACHER` + `R_SERVICE` |
| **可证伪切换条件** | M1 实测：Taro 主包 gzip > 1.2MB，或 tabBar 首屏冷启 → 可交互 > 2.5s → **立即切 uni-app 或原生，不改范围** |

### 1.1 我为什么同意 F 而不做全量（不是"保守"，是算账）

| 事实 | 数字 | 含义 |
|---|---|---|
| 业务 `.vue` 总数 | **48 个** | 按目录统计会严重低估（25 目录，`shared/` 无页面） |
| `views/` 总行数 | **27,911** | — |
| Element Plus 组件用量 | **2,401 处 / 57 种** | 全部需重写 |
| 前端依赖体积 | EP 188KB(gz) + ECharts 246KB(gz) = **36%** | 框架税 > 业务代码（业务 chunk 仅 ≈318KB gz） |
| 四桶分级 | P0 30.0% / P1 38.9% / P2 4.1% / NO-GO 26.9% | P0+P1 才是价值主体，P2/NO-GO 占 31% 是纯负担 |

**结论**：全量的成本主要在「重写 2,401 处 EP 用法」，而这部分**不产生新价值**——员工在手机上需要的只是那 7 个动作。做全量 = 花 70% 力气重做 31% 用不到的页面。

### 1.2 反方意见（我认真对待的三条，`architect` 原文见 `01` §5）

| 反方 | 我的裁决 |
|---|---|
| **「纯 web-view 1–2 周就能上」** | **部分成立**。若目标只是「手机上能看」，web-view 够用，且一麦已有 15 页卡片化 + 3 个公开 H5 分享页。但它拿不到**分享卡片、订阅消息、微信授权登录**这三样——而 P2 合规硬门恰恰要求微信授权登录。**所以 web-view 不能作为终局**，只能作探路。 |
| **「uni-app 比 Taro 更小更快」** | **存疑但无法先验排除**。已把它写成 M1 的**可证伪闸门**（主包 gzip >1.2MB 或首屏 >2.5s 即切）。这比现在争论更有价值。 |
| **「这个项目根本不该做」** | **已被部分证伪**。原本的论证依赖「免登录是净增量」，但合规侧发现「必须微信授权登录」是**强制项**而非增量——这一条反而**削弱了"不做"的理由**（因为不做就等于现有 web 在微信内体验永远拿不到授权登录与分享能力）。但 ROI 仍取决于 §2 的两个价值点是否成立。 |

### 3.2 我亲自推翻过的一条错误结论（写在这里防止后续引错）

我曾用字面量 grep 得出「浏览器依赖仅 49 处、集中 3 个文件，所以逻辑层几乎可直搬」，并把它当作可行性最强证据发给两个成员。**该结论错误，已撤回。**

**推翻依据（三层，逐层加深）**：

1. `api/ai.ts:1-3`、`api/yimai.ts:1-2` 均 import pinia store；
2. 三个 store 全部 `storage: localStorage`（`user.ts:284`、`yimai.ts:1044`、`ai-config.ts:408`），`store/index.ts:39` 还有全局默认；
3. **最深一层（`optimizer` 补，我已验证）**：`api/ai.ts:2` → `store/modules/yimai.ts:3` → `store/modules/user.ts:37` → `import { router } from '@/router'` → `router/index.ts:9-12` **`createWebHashHistory(...)` 在模块求值期执行**。

**所以最小可切单元是「api + store + 存储介质 + 路由依赖」四块，不是三块。** 摘掉 `user.ts:37` 那行 `import { router }` 是单点收益最大的动作。

**方法论纪律**：任何「依赖规模」结论必须先用已知为真的样本反向验证口径。本项目 `<el-` 返回 0 而 `<El` 返回 2,401，就是口径错误的直接信号。

### 3.3 全仓最值钱的单文件

`api/ai.ts`（4,007 行）中 **3,887 行是纯 prompt 常量与文本规则**（`MOMENTS_CATALOG` / `XHS_TOPIC_CATALOG` / `buildLengthRule` / `buildEmojiRule`），`USE_BACKEND` 仅 8 处、HTTP 分支正文 10 行。**营销工具迁移时生成质量调控全在这里，不用重写。**

`api/payroll.ts`（925 行）传递闭包只有 `./backend` 一个模块，是**唯一真正零间接依赖**的 api 文件。

## 7 需要队长拍板的决策点（都是选择题）

### D1 ⚠️ 最急：`nbyimai.com` 的 ICP 备案号与主体是什么？

- **A. 已备案，主体就是「一麦瑜伽」相关企业/个体户** → 直接用 `oa.nbyimai.com`，M0 可立即推进
- **B. 已备案，但主体是别的（个人 / 其他公司）** → 先做**变更备案**（最慢 1–20 天），M1 前必须完成
- **C. 未备案 / 不清楚** → 我出一份「查备案 + 补备案」的操作清单，但 M0 周期按 20 天算

> 我从 `DEPLOY.md` 和代码里都查不到备案号，**这条只能你给**。

### D2 小程序主体类型？

- **A. 企业/个体工商户**（推荐）→ 可开微信支付、类目不受限、可上「商业服务-企业管理」
- **B. 个人** → **不能开通微信支付**，部分类目受限；若只做内部工具且永不收款，勉强可走，但审核更严

### D3 价值判定（Go/No-Go）

`architect` 的原始判据是「分享卡片 / 订阅消息 / 免登录 三条净增量不足 2 条则立项不成立」。**但合规侧已把「免登录」变成强制底线（微信授权登录是合规要求，不是增量）**，所以判据要改成两条：

- **A. 分享卡片 + 订阅消息两条都成立** → **Go**，全案推进
- **B. 只成立一条** → **谨慎 Go**：先做 M0′ web-view 套壳（1–2 周），拿到真实使用反馈再决定是否投 M1/M2
- **C. 两条都不成立** → **No-Go**：改做 PWA / 优化现有 H5 移动端，不投小程序

> 我的倾向是 **B**。理由：一麦已有 15 页卡片化 + 3 个公开 H5 分享页，web-view 套壳 1–2 周就能让员工"在微信里用起来"，**先用最低成本验证员工到底会不会用**，再决定要不要为那 7 页付 4–6 周重写成本。这个顺序比拼速度更重要。

### D4 谁来做？

- **A. 你自己 + 我（AI 协作）** → 可行，但 M2 的 4–6 周是硬工作量
- **B. 外包** → 需要把本文档 + `03` 分级矩阵作为需求书交付
- **C. 先只做 M0′ web-view**（1–2 周），验证后再定 B/A

## 8 明确不做的事（NO-GO，写死在方案里）

| 不做 | 为什么不该进小程序（不是"做不了"） |
|---|---|
| **数据备份 / 恢复** | 不可逆覆盖生产库。手机误触代价无法承受 |
| **在线版本更新** | 替换在线产物，等同远程改生产环境 |
| **薪酬计算** | 银行卡号 / 个税属敏感个人信息，且金额误算不可撤回 |
| **AI 模型配置** | API 密钥中枢，暴露面最小化原则 |
| **人员管理** | 权限中枢。手机上误改角色会把人锁在门外 |
| **KeepYoga 同步** | 半同步状态需看产物文件对账，手机上无法完成核对 |
| **富文本编辑**（wangEditor） | 官方明示「暂不支持移动端编辑」，只支持查看 |
| **小程序内任何收款** | 预付卡需备案公示材料，小馆拿不到；且需「商家自营-预付卡」类目 |
| **ECharts 全量图表** | 主包 2MB 必爆；`useChart` 无法复用；`map/geo/visualMap/toolbox` 实际 0 处使用 |
