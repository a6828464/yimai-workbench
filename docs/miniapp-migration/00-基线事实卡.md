## 4.1 响应形态实测：不是 3 种，是 7 种（captain 已核验源码）

`api/backend.ts` 的 `unwrap()`（:52-68）只在 **HTTP 2xx 成功分支**执行；`http.interceptors.response.use` 的第一个参数 `(resp) => resp` 原样透传，错误分支（:80-99）只处理 `401`（触发 `expireSession`）与 `403`（把 `message` 归一为「无权限执行此操作」）。

由此得到 7 种形态及其在小程序里的行为：

| # | 形态 | 触发场景 | web 端怎么活下来 | 小程序里会怎样 |
|---|---|---|---|---|
| 1 | `{code:0, data}` | 正常成功 | `unwrap` 返回 `data` | 正常 |
| 2 | `{code:1, message}` | 业务失败（HTTP 200） | `unwrap` 抛 Error | 正常（复刻 unwrap 即可） |
| 3 | `{ok:true, data}` | 兼容形态 | `unwrap` 读 `data` | 正常 |
| 4 | `{errno, emsg}` | KeepYoga 风格 | `unwrap` 判 `errno!==0` 抛错 | 正常（复刻即可） |
| 5 | `{message, errors}` | **422 校验失败** | **axios 走错误分支**（非 2xx）→ Promise.reject | ⚠️ **wx.request 的 success 回调照常触发**（官方原文：只要收到返回，无论 statusCode 多少都进 success）→ 无 `code`/`ok`/`errno` → `unwrap` 原样返回 `undefined` → **静默判成功** |
| 6 | `{message:'Unauthenticated.'}` | **401 token 失效** | axios 错误分支 → `expireSession()` → 跳登录 | ⚠️ 进 success、无字段 → 静默判成功；**登出永不触发**，UI 显示"全空" |
| 7 | `{message:'账号已停用'}` | **403 停用** | axios 错误分支 → 归一 message | ⚠️ 同上，静默判成功，用户看到空白无提示 |

**两处例外**（`be-analyst` 指出，captain 采信待抽查）：`logout` 返回 `{code:0}` 无 `data`；`PayrollController.php:775` 的 `code` 是字符串。

**结论**：小程序侧**必须**复刻两层逻辑，缺一不可——
1. **`statusCode` 闸门**：`wx.request` 的 `success` 里先判 `res.statusCode`，非 2xx 一律当失败（这是 web 端由 axios 免费提供的、小程序里没有的东西）；
2. **`unwrap` 三形态解包**：`{code}` / `{ok}` / `{errno}` 各自分支，且 `{code}` 要兼容字符串。

否则会出现三种真实故障：**密码错显示"登录成功但白屏"**、**token 过期"页面全空且登出永不触发"**、**账号停用"空白无提示"**。这不是理论风险，是「照抄 web 的 fetch 写法」必然踩的坑。

### 6.7 **撤回记录**：字面量 grep 会漏掉间接依赖（captain 自查推翻）

**推翻依据**：`api/ai.ts:1-3` 与 `api/yimai.ts:1-2` 首行即 import 三个 pinia store：

```
ai.ts:1   import { useAiConfigStore, SERVER_CONFIGURED_PLACEHOLDER } from '@/store/modules/ai-config'
ai.ts:2   import { useYimaiStore } from '@/store/modules/yimai'
ai.ts:3   import { useUserStore } from '@/store/modules/user'
yimai.ts:1 import { useUserStore } from '@/store/modules/user'
yimai.ts:2 import { useYimaiStore } from '@/store/modules/yimai'
```

而这三个 store 全部把 `localStorage` 作为持久化介质：

```
store/modules/user.ts:284      storage: localStorage
store/modules/yimai.ts:1044    storage: localStorage
store/modules/ai-config.ts:408 storage: localStorage
store/index.ts:39              storage: localStorage   （createPersistedState 全局默认）
store/modules/user.ts:190,206,236,255  直接读写 localStorage（含 backend-token）
```

**正确结论**：逻辑层对浏览器的依赖**不是 49 处，而是「字面量 49 处 + 经 pinia 持久化间接依赖」**。`ai.ts` / `yimai.ts` 这两个占逻辑层 50% 的大文件，**无法原样搬进小程序**——它们依赖的 store 层把 `localStorage` 焊死在持久化配置里。

**对可行性的真实影响**：
- 跨端复用的**真正单位不是 `api/*.ts` 文件，而是「api + store + 存储适配」这一整层**。
- 适配层必须覆盖 `pinia-plugin-persistedstate` 的 storage 介质切换（→ `wx.setStorageSync` 封装），否则整个 state 层在小程序里直接崩。
- 这**没有否定可行性**，但把「改 3 个文件」的工作量修正为「改 3 个文件 + 抽存储适配层 + 处理 4 处直接读写」，并且这一层是**所有页面共享的底座**，必须先做。

**方法论教训**（写给下游成员）：只对字面量做 grep 会系统性低估依赖。判断跨端可复用性必须沿 import 链走到叶子节点，或直接用打包产物验证（如 `vite build` 后看 chunk 里是否含 `localStorage`）。

| C6 | 数据合规 | 会员手机号/体测数据/健康信息属**敏感个人信息**，小程序侧收集需单独同意（《个人信息保护法》+ 微信隐私协议规范） |
