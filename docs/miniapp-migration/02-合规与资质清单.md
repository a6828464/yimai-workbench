**关键认知**：服务类目审的是「**小程序对外提供的服务内容**」，不是「这个软件的商业定位」。审核硬规则是「**小程序首页必须能直达或两次点击内到达所有申报类目的页面**」（[常见拒绝情形](https://developers.weixin.qq.com/miniprogram/product/reject.html) 3.1.2）。所以类目不是随便挑一个「无资质」的就行——**申报的类目必须被首页真实功能支撑**，否则触发「类目不符行为」（运营规范 2.5.7）。

### 1.2 类目优先级排序（我的判断）

1. **主类目 `商业服务-企业管理`** —— 一麦的核心页（会员/客资/排课/薪酬/审批/报表）本质是「门店信息管理 + 办公管理」，与官方适用范围文字几乎逐字对应，且**零额外资质**。
2. **辅类目 `工具-健康管理`** —— 只在**确实要展示体测数值**时加，用于安放「身高/体重/体脂/围度 + 历史趋势」这类**记录型**内容。
3. **备选 `体育-体育场馆服务`** —— 若小程序里出现「场馆/课程预约」入口再加。
4. **备选 `生活服务-丽人服务（瑜伽）`** —— 只有当你想让小程序在类目上「看起来是瑜伽馆」时加；注意该类目官方备注明确「不含医疗美容」，说反了就是类目不符。
5. **永不选**：`教育服务-*`（要办学许可证）、`医疗服务-*`（要医疗机构执业许可证）。

> **为什么不用教育类**：`教育服务-非学科类培训机构` 的资质是 4 选 1 的许可证件，瑜伽馆通常只有营业执照；而且小程序**备案**里「校外培训」还是一项**前置审批**——备案时要提交「教育部门允许开展校外培训的审批文件」（[小程序备案操作指引](https://developers.weixin.qq.com/miniprogram/product/record/record_guidelines.html) 二·2 前置审批材料表）。选教育类 = 同时卡类目 + 卡备案两道，纯亏。

### 1.3 纯员工内部使用，能不能降低资质要求？

**分两件事说，别混**：

- **类目资质**：降不了，但**也不需要降**——上表前 5 个候选的「资质要求」列本来就是「/」，即除营业执照外不要任何行业许可。所以「内部使用」在这里没有让资质变松，是**这个类目本身就不要资质**。
- **审核门槛**：**不降反升**。三条硬规则直接顶上来：
  1. 「若小程序中存在账号体系，**需提供测试号**，包含账号和密码（**可以体验所有功能**）」——3.3.4；
  2. 「小程序的功能应具有使用价值，**不能过于简单**」——3.1.5；
  3. 「若存在隐藏或付费功能（仅会员可见等受限功能点），**开发者提供的测试号需可完整呈现和体验该功能**」——3.1.4。
  → 员工专用 = 全员受登录墙保护 = 审核员什么都看不到 = **必须交测试号，且测试号要能看到真数据**。这是「内部工具」类小程序最常见的驳回点。
- **唯一真正能「不做对外合规」的路径**：不发布正式版，只走**体验版/开发版**给员工用。但体验版有成员上限、不能对外传播、且**小程序备案在发布前仍要办**（备案是发布前置，见 §2）。这条路径不解决合规，只规避「公开运营」。

**结论**：内部使用**不能**作为降低类目或备案要求的理由；它只会让「测试号 + 功能完整性」这两项审核要求变得更硬。

### 1.4 队长特别问：含「体测/身体评估」会不会触发额外类目？

**会，取决于「展示什么」。**

- 类目表里 `工具-健康管理` 的适用范围是「**记录/测试**与健康相关内容，如身高、体重、个人身体管理记录」——注意它写的是「记录」，不是「评估/诊断/建议」。
- `医疗服务-其他私立医疗机构`/`互联网医院` 等三级分类全部要求《医疗机构执业许可证》。一麦是瑜伽馆，**没有**该证。
- 一麦现在存的体测数据**不只是数值**：`body_test_reports` 表里有 `composition`（体成分逐项：值/档位/标准区间/**风险与建议**）、`abnormal`（异常项）、`posture`（体态异常项）、`health`（健康问卷）、`red_flags`（红线提示）、`observations`（训练观察项）——见 [2026_09_15_000003_create_body_test_reports.php:33-45](backend/database/migrations/2026_09_15_000003_create_body_test_reports.php#L33-L45)。

**判断**：数值 + 趋势 = 「记录」，安全；**「风险/异常/红线/建议」= 「健康评估」，踩线**。小程序侧建议：
1. 只展示 `profile`（身高/体重/BMI/体脂率）+ 历史趋势；
2. `abnormal` / `red_flags` / `composition.建议` **不进小程序**，留在 PC 后台；
3. 页面固定标注「数据来源：门店体测设备原始报告，**非医疗诊断**，不构成医疗建议」；
4. 一旦出现「改善XX疾病 / 治疗 / 康复处方」字样，即触发运营规范 2.6.4.7（医疗健康类夸大/不实）与医疗类目要求。

## 2 服务器域名（C3 落地）

### 2.1 官方硬要求（原文要点，[网络·使用说明](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)，2026-11-03）

- 只允许 HTTPS（`wx.request` / `uploadFile` / `downloadFile`）与 WSS；
- **域名不能是 IP 或 localhost**；
- 可以配端口，但**配了端口就只能走该端口**（配 `https://x.com:8080` 后请求 `https://x.com` 会失败；不配端口时连默认 443 也不能写）；
- **域名必须经过 ICP 备案**；
- **不支持配置父域名、使用子域名**（要配 `oa.nbyimai.com` 这个完整子域）；
- 证书：必须有效、域名一致、在有效期、**信任链完整**、iOS 不支持自签名、**TLS 必须 1.2 及以上**、iOS 需满足 ATS；
- 配置位置：**小程序后台 → 开发 → 开发设置 → 服务器域名**。

### 2.4 小程序主体 与 域名备案主体 不一致，会卡在哪一步？

- **小程序备案本身**（2023-09-04 起开放）：要求「主办单位证件 + 主体负责人证件 + 小程序负责人证件 + 负责人**人脸核身**」，走「平台初审 1–2 工作日 → 工信部 12381 短信核验（24 小时内）→ 通管局 1–20 工作日」（[备案操作指引](https://developers.weixin.qq.com/miniprogram/product/record/record_guidelines.html) 三）。**这里的备案主体 = 小程序主体**，与域名备案是**两套独立备案**。
- **微信侧对「域名备案主体是否必须等于小程序主体」**：本次在《运营规范》《常见拒绝情形》《网络·使用说明》《备案操作指引》四份文档中**均未找到明文规定**。→ **未找到官方依据，需向微信客服/当地通管局确认**。
- **实践会卡的地方（标注：非官方明文，属风险提示）**：
  1. 域名若备案在他人（如前员工、代运营公司）名下 → 域名控制权不在自己手上，小程序上线后对方可随时改解析；
  2. 涉及支付/资质类审核时，主体链路不一致会被要求补充授权；
  3. 用户投诉/内容违规追责时，域名主体与小程序主体分离会造成责任不清。
- **结论**：按「**一致**」准备，别赌。若 `nbyimai.com` 备案在个人名下而小程序要走企业主体 → **先做备案变更**，这是最长的一条前置链（变更备案同样走通管局审核）。

## 3 登录合规（C4，结论最硬的一条）

### 3.1 直接结论

**不能只保留现有的 Bearer Token 账号密码登录。**

依据（原文）：《微信小程序平台运营规范》**2.12 技术实现规范 → 6. 授权登录**：「**微信小程序内存在账号体系时，必须提供微信授权登录。**」（[运营规范](https://developers.weixin.qq.com/miniprogram/product/)，2026-11-03 抓取，该条位于 2.12 节「其他要求」列表内）

- 一麦**有账号体系**（`users` 表 + 登录页 + Bearer Token），见 [routes/api.php:60](backend/routes/api.php#L60)、[AuthController.php:35](backend/app/Http/Controllers/AuthController.php#L35)、[sanctum.php:53](backend/config/sanctum.php#L53)（Token 14 天）。
- 因此：**账号密码登录可以保留，但必须并列提供「微信授权登录」入口**。只给账号密码 = 规范违反，运营阶段可被处置。

### 3.2 顺带澄清三个常见误解

| 误解 | 事实 |
|---|---|
| 「小程序禁止账号密码登录」 | **没有这条禁令**。《常见拒绝情形》3.4.2 禁的是「请求或诱导用户输入**微信用户的**用户名或密码」——禁的是**微信账号密码**，不是自家账号密码。 |
| 「wx.login 是强制的」 | 官方**没有**「所有用户必须 wx.login」的表述。强制的是「**有账号体系就必须提供微信授权登录**」这个能力入口（2.12-6）。 |
| 「用了 wx.login 就不能再用自己的 Token」 | 可以。官方登录文档明确：拿到 code → 服务端 `auth.code2Session` 换 openid/session_key → 「**开发者服务器可以根据用户标识来生成自定义登录态**」（[小程序登录](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)）。 |

### 3.3 技术映射（只写方案，不写实现）

现有链路：`POST /api/auth/login`（账号密码，`throttle:10,1`）→ Sanctum `createToken('workbench')` → 前端存 Bearer → 14 天过期。

合规改造的**最小改动面**：
1. 新增服务端端点（如 `/api/auth/wechat`）：接收 `wx.login` 的 `code` → 服务端调 `code2Session`（**AppSecret 只存服务器，绝不下发**）→ 拿 `openid` → 匹配/绑定 `users` → **仍然签发 Sanctum Token**；
2. 小程序登录页并列两个入口：「微信一键登录」+「员工账号密码」；
3. 账号绑定关系落库（`users.openid` 或独立绑定表）——**注意这是新表/新字段，属代码改动，本轮不做**；
4. 保留「退出登录」（3.5.5 强制要求「账号系统必须有易于发现的退出选项」）；
5. 提交审核时准备**测试号**（3.3.4）。

**不用改的**：Token 机制、14 天有效期、`/api/*` 同域反代（[admin-web/.env.production](admin-web/.env.production) `VITE_API_BASE = /api`）。小程序直接请求 `https://oa.nbyimai.com/api/...` 即可，无需改后端路由结构。

### 3.4 头像昵称新规（现状，2026-11-03）

- `wx.getUserProfile` 文档首行已标注：「**用户头像昵称获取规则已调整**，参考《小程序用户头像昵称获取规则调整公告》」——即**旧接口拿不到真实头像昵称**了（[wx.getUserProfile](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/user-info/wx.getUserProfile.html)）。
- 现行做法（[获取头像昵称](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/userProfile.html)）：
  - 头像：`<button open-type="chooseAvatar" bindchooseavatar=...>`（基础库 **2.21.2** 起）；
  - 昵称：`<input type="nickname">`（键盘上方展示微信昵称）；
  - 基础库 **2.24.4** 起接入内容安全（`mediaCheckAsync` / `msgSecCheck`），未通过则**不触发回调 / 清空输入**。
- 对一麦的影响：`users.avatar` / `users.name` 字段可继续用，但**获取入口必须换**；员工头像建议干脆用姓氏首字母占位，减少一个隐私接口。

### 3.5 手机号快速验证组件（`getPhoneNumber`）使用条件

- **仅对「非个人主体」且「已完成认证」的小程序开放**（[手机号快速验证组件](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/getPhoneNumber.html)）；
- **收费**：2023-08-28 起 **0.03 元/次**（调用成功才扣），每个账号 **1000 次体验额度**（正式/体验/开发版共用）；
- `getPhoneNumber` 返回的 `code` 与 `wx.login` 的 `code` **不能混用**，各自 5 分钟有效、一次性；
- 一麦场景：会员手机号本来就是**门店录入**的，**不需要**用这个组件向用户索要手机号——省一笔钱也少一个隐私接口。

## 4 个人信息与敏感数据（C6）

### 4.1 微信侧强制要求（三条，都是硬拦截）

1. 「涉及处理用户个人信息的小程序开发者，**均需补充**相应用户隐私保护指引」；
2. 「**仅有在指引中声明所处理的用户信息，才可以调用平台提供的对应接口或组件。若未声明，对应接口或组件将直接禁用**」；
3. 提审时「若隐私接口调用情况与隐私协议内容有出入，或隐私协议内容为空，则**在提审时会提醒开发者进行更新**（被拦截）」。
   —— 以上均出自 [用户隐私保护指引填写说明](https://developers.weixin.qq.com/miniprogram/dev/framework/user-privacy/) 与 [隐私协议开发指南](https://developers.weixin.qq.com/miniprogram/dev/framework/user-privacy/PrivacyAuthorize.html)（2026-11-03）。

**实现要点**：`wx.getPrivacySetting` 查 `needAuthorization` → 需要时弹自定义隐私弹窗 → 用 `<button open-type="agreePrivacyAuthorization">` 收集同意 → 之后才能调已声明接口。同意状态**按接口粒度**同步（新增接口需重新同步）。

### 4.2 一麦的实际数据盘点（源码锚点）

| 数据 | 位置 | 敏感级别 |
|---|---|---|
| 会员手机号 | [2026_08_26_000001_create_yimai_tables.php:24](backend/database/migrations/2026_08_26_000001_create_yimai_tables.php#L24)（`customers.phone`）、`:47-48`（`phone_tail`） | 敏感（PIPL 28 特定身份/联系方式） |
| 体测：身高/体重/BMI/体脂率 | `body_test_reports.profile`（[同文件:33-45](backend/database/migrations/2026_09_15_000003_create_body_test_reports.php#L33-L45)） | **敏感·医疗健康** |
| 体测：体成分/异常项/体态/健康问卷/红线 | `composition` / `abnormal` / `posture` / `health` / `red_flags` / `raw` | **敏感·医疗健康（最高）** |
| 消费记录 | `ky_cards`、销售/耗卡统计 | 敏感（金融账户相关） |
| 员工账号/薪酬 | `users`、`payroll` 相关表 | 员工个人信息 + 薪酬（高） |

### 4.3 法律要求（PIPL，原文抓自 cac.gov.cn）

- **第 28 条**：敏感个人信息包括「生物识别、宗教信仰、特定身份、**医疗健康**、金融账户、行踪轨迹等」；「只有在具有**特定的目的和充分的必要性**，并采取**严格保护措施**的情形下」方可处理。
- **第 29 条**：处理敏感个人信息「应当取得个人的**单独同意**」。
- **第 30 条**：还应「向个人告知处理敏感个人信息的**必要性**以及对个人权益的**影响**」。
- **第 55 条**：处理敏感个人信息前，**应当事前进行个人信息保护影响评估**，记录至少保存 3 年。
  来源：[《中华人民共和国个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)，2026-11-03。

### 4.4 「单独同意」怎么落地（可验收的四件事）

1. **隐私指引分层**：在《小程序用户隐私保护指引》里把「会员体测数据（健康信息）」**单独列为一项**，不与「手机号」混在一条里；
2. **独立同意浮层**：进入体测页时弹**独立**弹窗（标题写明「体测数据（含健康信息）处理」），**不能与总隐私协议用同一个勾选框**；同意后记录 `同意时间 / 版本号 / openid`（一麦已有 `audit` 模块，可复用——**需技术侧确认表结构**）；
3. **告知必要性**：文案必须写清「为什么需要」+「对你不利的影响」（例：「本数据用于教练制定训练计划；不提供将无法查看历史体测对比」）；
4. **撤回与删除**：提供撤回入口，且用户要求时应删除（运营规范 2.5.12 第 4 条：「若用户要求，你应该删除接收的所有关于该用户的数据」）。

**另外两件容易漏的**：
- **员工看会员数据 = 处理他人敏感信息**：需要内部授权 + 最小必要（PIPL 6）。一麦的「门店隔离（venue）」机制是技术基础，但**权限分层与日志**要在方案里写清；
- **个人信息保护影响评估（PIA）**：PIPL 55 要求「处理敏感个人信息」前做评估并留记录 ≥3 年。**这是文档动作，不是代码动作**，队长需要一个模板（可先出一页纸自评）。

### 4.5 组件与能力的合规使用条件（汇总）

| 能力 | 条件 | 依据 |
|---|---|---|
| `wx.getUserProfile` | 已调整，**不要再用**来拿头像昵称 | 官方 API 文档首行 |
| `chooseAvatar` + `input type=nickname` | 基础库 2.21.2+；2.24.4+ 接内容安全 | 获取头像昵称文档 |
| `getPhoneNumber` | 非个人主体 + 已认证 + 0.03 元/次 | 手机号快速验证文档 |
| `wx.getPrivacySetting` / `agreePrivacyAuthorization` | 基础库 2.32.3+（查询）；同意按钮 | 隐私协议开发指南 |
| 拒绝授权后 | **不得**自动退出/关闭/停止全部服务 | 运营规范 2.15 |

## 5 支付（C5）

### 5.1 小程序内收款只能走微信支付

- 虚拟商品（虚拟代币、解锁功能、订阅、付费功能、打赏）→ **必须**接入「小程序虚拟支付」，且「**不得引导至 app、公众号、h5、个人号、网站完成支付**」（运营规范 2.5.13）。
- 一麦的会员卡/课时费属**服务类预付**，不是虚拟商品 → 走**微信支付 JSAPI（小程序支付）**。

### 5.2 资质链路（三步，缺一不可）

| 步 | 要求 | 依据 |
|---|---|---|
| ① 微信认证 | 支持主体：**个体工商户 / 企业 / 媒体 / 政府及事业单位 / 其他组织**——**不含「个人」**；且「认证成功不作为提交发布审核的前提，**但支付功能等腾讯有特别规定的除外**」→ **支付需认证** | [微信认证指引](https://developers.weixin.qq.com/miniprogram/product/renzheng.html) |
| ② 申请商户号 | 普通商户入驻支持主体：**个体工商户、企业、政府机关、事业单位、社会组织**——**不含个人** | [mchid与appid申请](https://pay.weixin.qq.com/doc/v3/merchant/4012071573) |
| ③ 绑定 appid | 商户号必须与小程序 appid 绑定后才能收款 | 同上 |

### 5.3 瑜伽馆能不能开通？能，但「卖预付卡」是另一码事

**能开通的部分**：个体工商户/企业主体 → 微信认证 → 申请商户号 → 绑定 appid → 可做「单次课/单笔订单」收款。

**会卡住的部分**：**会员卡/课时包 = 预付卡**。
- 微信类目 `商家自营-预付卡（发行方）` 的资质要求：《单用途预付卡》**备案公示材料** 或 《支付业务许可证》（[类目表](https://developers.weixin.qq.com/miniprogram/product/material/)）。适用范围原文就写着「**会员卡预充值**、储值卡购买」。
- 商务部《单用途商业预付卡管理办法（试行）》要点（[商务部令第 9 号](https://www.mofcom.gov.cn/zfxxgk/zc/gz/art/2021/art_82805c1937a64a4186ea15c23fc675c5.html)，2026-11-03）：
  - 第 2 条：适用「零售业、住宿和餐饮业、**居民服务业**」的**企业法人**（**注：瑜伽馆是否落入附件 1 的「居民服务业」分类，需核对附件 1 行业分类表——本次未抓取附件，标为待确认**）；
  - 第 7 条：**发卡企业应在开展单用途卡业务之日起 30 日内备案**；集团/品牌→省级，规模→设区市，**其他发卡企业→县（市、区）商务主管部门**；
  - 第 4 条：规模发卡企业 = 上一会计年度营收 **500 万元以上**，或注册不足一年且注册资本 **100 万元以上**；
  - 第 18 条：**单张记名卡 ≤ 5000 元**；不记名卡 ≤ 1000 元；
  - 第 19 条：**记名卡不得设有效期**。

**现实卡点**：小瑜伽馆通常不是「规模发卡企业」，但按第 7 条仍属「其他发卡企业」需备案；而类目审核要的是「**备案公示材料**」——**没备案就拿不出这份材料，类目就可能过不了**。

### 5.4 结论与建议路径

| 场景 | 结论 |
|---|---|
| **当前阶段（员工内部工具）** | **不要**在小程序内开放收款。只做「课时核销 / 预约 / 账单展示」，不出现「充值 / 储值 / 购卡」按钮 |
| 后续要做「单次课/体验课」收款 | 可行：认证 + 商户号 + appid 绑定即可，不涉预付卡类目 |
| 后续要做「会员卡/课时包」线上销售 | 必须先解决：① 当地商务部门单用途卡备案（拿公示材料）；② 加 `商家自营-预付卡` 类目；③ 卡面额与有效期符合第 18/19 条。**周期以月计，且各地口径不一** |
| 想绕开（引导线下转账/个人收款码） | **不行**：运营规范 2.5.13 明确禁止引导站外支付；且预付卡本身仍受商务部办法约束 |

| **诱导分享** | 中 | 若任何页面出现「转发朋友圈领课时/领券」→ 2.5.1 直接违规。一麦另有一个**站外 H5**「朋友圈素材站」（记忆记录为 `pyq.shunan.fun`，**属记忆来源，未在本仓库核实**），不要在小程序内复制这套「转发换利益」机制 |

**建议（不改代码，只给取舍）**：
1. 营销模块**不进小程序**，继续留在 PC 后台 + 独立 H5。理由：它是「生产广告的工具」，在小程序里既拿不到加分，还引入 3.2.2 与内容安全风险；
2. 若一定要进，**不能放首页/首屏**，且页面要有明确「内部工具，内容仅员工可见」的定位，不出现广告位；
3. 成稿侧加一道**关键词黑名单**（疗效/绝对化/承诺类），命中即标红提示，**不允许一键复制**；
4. 小红书/朋友圈**成稿文本**属 UGC 边界，若小程序展示历史记录，需接 `msgSecCheck`（运营规范 2.5.18）。
